# Ameen Demo Visuals

## Purpose

This document defines the visual assets needed for the Ameen product demo, sales deck, and website.

The demo must help customers understand the product without needing a live production system or real customer data.

## Demo Story

The demo should show a fictional Saudi organization preparing for a cybersecurity readiness assessment.

Recommended fictional organization:

> Najd Digital University

The demo should show a realistic but fictional scenario:

- Policies are scattered.
- Evidence is incomplete.
- Management wants to know readiness.
- The compliance team needs a clear action plan.
- Ameen converts documents into a readiness view.

## Visual Asset 1: Before Ameen

Show a messy state:

- Many documents
- Spreadsheet trackers
- Email approvals
- Evidence folders
- Manual consultant notes
- Unclear control status

Message:

> Compliance work is not missing effort. It is missing structure, traceability, and continuous visibility.

## Visual Asset 2: Ameen Journey Diagram

Show the simple customer journey:

1. Create Organization
2. Upload Documents
3. AI Analyzes
4. AI Maps Controls
5. Customer Reviews
6. Upload Evidence
7. Readiness Dashboard

This diagram must appear in:

- Website homepage
- Product page
- Sales deck
- Demo intro
- Proposal template

## Visual Asset 3: Document Upload Mockup

Show a clean interface with sample uploaded documents:

- Information Security Policy
- Access Control Policy
- Incident Response Procedure
- Business Continuity Plan
- Vendor Security Policy
- Backup and Recovery Procedure

Each document should have a status:

- Uploaded
- Classified
- Mapped
- Needs Review

## Visual Asset 4: AI Mapping Mockup

Show how Ameen maps document content to controls.

Include:

- Control ID
- Control title
- Matched document section
- AI explanation
- Confidence level
- Human decision buttons

Buttons:

- Accept Suggestion
- Reject Suggestion
- Needs More Evidence

## Visual Asset 5: Readiness Dashboard Mockup

The dashboard should show four dimensions:

- Documented
- Implemented
- Evidenced
- Verified

Avoid showing one generic compliance percentage. The purpose is to teach that documentation alone is not enough.

Recommended cards:

- Documented Readiness
- Evidence Readiness
- Verified Readiness
- Open Gaps
- Pending AI Suggestions
- High-Priority Controls

## Visual Asset 6: Evidence Guidance Mockup

Show a control that needs evidence.

The UI should show:

- Official requirement
- Ameen advisory evidence examples
- Uploaded evidence
- Missing evidence
- Reviewer notes

Example evidence types:

- Approved policy
- Access review records
- System configuration screenshot
- Incident test report
- Backup test result
- Awareness training records

## Visual Asset 7: Executive Report Preview

Show a professional report export:

- Executive summary
- Readiness score by dimension
- Top gaps
- Evidence status
- AI suggestions reviewed
- Human approval summary
- Recommended next actions

The report should look board-ready, not like a raw system export.

## Visual Asset 8: Trust Architecture Diagram

Show:

- Customer-controlled deployment
- Local analyzer option
- Optional external AI provider
- Human approval gate
- Audit trail
- Evidence repository

This visual supports government and regulated customer discussions.

## Visual Asset 9: Framework Status Grid

Show framework availability honestly:

- ECC: Pilot-ready after legal and review gates
- CCC: Imported, not broadly published until review
- TCC: Imported, not broadly published until review
- OSMACC: Imported, not broadly published until review
- DGA/Qiyas: Planned
- PDPL: Planned

The website should not imply that every framework is production-ready today.

## Visual Asset 10: Pilot Timeline

Show a 60-90 day pilot timeline:

### Week 1

Kickoff, scope, deployment model, sample documents.

### Weeks 2-3

Document upload, classification, AI mapping review.

### Weeks 4-6

Evidence upload, readiness dashboard, gap review.

### Weeks 7-8

Executive report, feedback, commercial decision.

### Weeks 9-12

Optional expansion, additional departments, roadmap alignment.

## Demo Design Rules

The demo must be:

- Simple
- Visual
- Executive-friendly
- Honest
- No fake regulatory claims
- No real customer data
- No complex backend explanation unless asked

## Demo Do Not Show

Do not show:

- Raw database tables
- Engineering logs
- Security defects
- Incomplete framework imports as if complete
- Real customer documents
- Secret keys or provider configs
- Unsupported certification claims

## Final Demo Goal

By the end of the demo, the customer should say:

> I understand how Ameen can reduce assessment effort and show readiness faster, but I also see that human review and evidence approval remain under our control.
